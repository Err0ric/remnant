# ADR-0015: AI usage visibility

Status: **Accepted** 2026-10-14 (project owner asked for all of it to be built and tested; defaults below are the conservative ones). Recorded as SPEC D41; threats T31 to T36.

## Context

Teams adopting AI tools need the same visibility they have for any other system: who uses which AI services, which agents and MCP servers are running, how much it costs, and whether anything unapproved has appeared. Today that takes a commercial observability product. The data already exists in places Remnant can reach:

- Firewall, DNS, and proxy logs already in the lake show traffic to AI services (shadow AI), for every vendor.
- Claude Code exports OpenTelemetry (OTLP) logs and metrics on every plan: sessions, tokens, cost, tool calls, MCP use, with `user.email`. Prompt text and tool arguments are redacted unless the admin turns them on.
- Anthropic's APIs report usage and cost (Admin API, API organizations), Claude Code activity per user (Claude Code Analytics API), claude.ai activity per user (Analytics API, Enterprise), and an audit feed (Compliance API activity feed; Enterprise, or Console organizations for the feed only).
- MCP client configuration files on endpoints list every MCP server a person has installed, approved or not.

Remnant treats AI tools as a data source like any other: deterministic ingest, nothing read by a model unless a person asks, every source `local_only` by default.

## Decision

| # | Question | Decision | Why | Alternative |
|---|---|---|---|---|
| 1 | Which services count as AI | A catalog in the repo, `backend/app/content/ai/services.yaml`: name, vendor, kind (`chat`, `api`, `coding`, `agent_platform`, `mcp_registry`, `image`), and domain suffixes. Admins add their own entries and mark any entry **Approved** or **Not approved** (stored in `meta.sqlite`, audited `ai.service_change`). Unmarked entries show as **Unreviewed** | One list drives the page, the rules, and the alerts; reviewable in a PR | Vendor App-ID names only (one firewall vendor, opaque names) |
| 2 | Shadow AI from network logs | A derived destination domain per event (`dst_endpoint_hostname`, else `unmapped.query`, `qname`, `url`, `url_filename`, `hostname`, with the host taken out of a URL), matched by suffix against the catalog. Read only through the caller's `events` view | Works on the DNS, firewall, and proxy templates already shipped; no new ingest | A separate enrichment pass at ingest (rewrites nothing today; can be added later) |
| 3 | OTLP receiver | `POST /api/otlp/v1/logs` and `/api/otlp/v1/metrics`, OTLP/HTTP with **JSON** (`http/json`); protobuf and gRPC answer 415 with a message naming `http/json`. One source of kind `otlp` per sender group, each with its own ingest token (shown once, stored hashed, revocable, audited `source.otlp_token`). Body capped at 4 MB, 2,000 records a request, 60 requests a minute per source; no session or CSRF (machine endpoint, bearer token only) | Standard exporters work unchanged (`OTEL_EXPORTER_OTLP_ENDPOINT=https://<host>/api/otlp`); the token can only write to its own source | gRPC listener (another port and dependency); one shared token (one leak exposes all) |
| 4 | What is stored from telemetry | Each log record or metric data point becomes one JSON line (flattened attributes, resource attributes under `resource`). By default the receiver **drops** prompt text, assistant response text, tool input and parameters, and raw API bodies, keeping only `mcp_server_name`, `mcp_tool_name`, `skill_name`, and sizes from tool parameters. An admin can turn on **Keep prompt and tool content** per source (audited `source.otlp_content`, warning shown). The stored line is `raw`, unchanged after that point | Usage visibility needs who, what tool, which MCP server, cost; it does not need what people typed. Minimizing at the door keeps HR-sensitive text out of the lake by default | Store everything and mask in the UI (still in the lake, still in backups) |
| 5 | Claude Code mapping | Template `claude_code_otel`: OCSF API Activity (6003); `actor_user_name` = `user.email`; `message` = event or metric name; `time` from the record; status from `success`; tokens, cost, model, tool, MCP names, session, terminal in `unmapped` | Searchable like any other log; Sigma and saved searches work on it | A bespoke table (would bypass guard, views, and access control) |
| 6 | MCP server inventory | (a) From telemetry: `mcp_server_name` in tool events, `mcp_server.name` on metrics, and `mcp_server_connection` events. (b) From endpoints: `scripts/endpoint/mcp-inventory.ps1` and `mcp_inventory.py` read the known client config files (Claude Desktop, Claude Code user and project files, Cursor, VS Code, Windsurf) and print one JSON line per server: host, OS user, client, server name, transport, command name or URL host. **Never** arguments, environment, or headers (they hold secrets). Output goes to a folder a file source reads, or straight to the OTLP receiver | Covers servers a person installed but never used, and clients that send no telemetry | Reading config files over the network from Remnant (needs endpoint credentials) |
| 7 | Approved MCP servers | An allowlist of server names (exact, or `prefix*`), admin-managed, audited `ai.mcp_change`. Every server seen is **Approved**, **Not approved**, or **Unreviewed** | Same review model as services; unknown is the interesting case | Blocklist only (misses new ones) |
| 8 | AI usage page | **AI usage** (nav, Detect group): tabs **Services** (by service: users, hosts, events, first and last seen, status), **Agents and MCP** (users, clients, MCP servers, tools, status), **Claude usage** (tokens and cost by user and model from telemetry or the Anthropic connectors), **Catalog** (admins: approve, add). All numbers come from the caller's `events` view, so people see only sources they may read | One place for the governance question; plain label in nav | Scattered dashboard panels |
| 9 | Alerts | An **AI watch** (admins, like the quiet-source watch): when a service or MCP server that is not Approved is first seen for a user or host, send one alert to chosen targets (ADR-0007 format, summary only: service or server name, user or host, first seen). First sightings kept in `ai_sightings` so restarts do not repeat them. Audited `ai.watch_change` and `ai.sighting` | "New unapproved AI thing" is the actionable signal; repeat traffic is not | A Sigma rule per service (no memory of "first seen") |
| 10 | Anthropic connectors | Source kind `anthropic`, one per key, with feeds: `usage` and `cost` (Admin key), `claude_code` (Admin or Analytics key), `analytics_users` (Analytics key, Enterprise), `compliance_activities` (Compliance or Admin key). Each record is one JSON line with `feed`; templates map them. Host fixed to `api.anthropic.com` over https with the pinned-address rules (ADR-0007 row 4). Key encrypted, write-only. **Never** the Compliance content endpoints (chats, files, projects, transcripts) | Matches what the vendor exposes per plan; the activity feed gives an audit trail without reading conversations | Pulling chats for DLP (out of scope; a different product with different consent) |
| 11 | Ingest, not the LLM gate | These connectors and the receiver are ingest. They never call a model and never pass through `llm/gate.py` | The gate is for sending data to models; this is reading data in | |
| 12 | Classification and access | All new sources default to `local_only`. The setup guides recommend a source group for AI usage data limited to the people who review it | Usage by named employees is HR-sensitive | |
| 13 | Sensitive-data signals (detective DLP) | Before dropping prompt and tool text, the receiver scans it for sensitive patterns (US SSN, payment card numbers with a Luhn check, AWS, GitHub, Slack, Anthropic, and OpenAI keys, private key blocks, JSON Web Tokens, password assignments) and stores only the categories and counts (`attr.sensitive`, `attr.sensitive_total`). The text is still dropped unless the source keeps content. Claude Code sends prompt text only with `OTEL_LOG_USER_PROMPTS=1` (and tool input with `OTEL_LOG_TOOL_DETAILS=1`); the guide explains that turning these on lets Remnant flag sensitive data without storing it. The AI watch can alert on any record with sensitive signals | Compliance needs "who sent what kind of data to an AI tool", not the data itself; blocking stays with inline tools (Purview Endpoint DLP, firewall DLP), whose events Remnant ingests | Storing prompts for later review (a sensitive data store of its own) |

## Consequences

- New: `app/ai/` (catalog, matcher, inventory, watch), `app/ingest/otlp.py`, `app/ingest/connectors/anthropic.py`, templates `claude_code_otel`, `mcp_inventory`, `anthropic_*`, endpoint scripts, an AI usage page, three small tables (`ai_service_status`, `ai_mcp_allow`, `ai_sightings`) and OTLP token columns on sources.
- The OTLP endpoint is a new unauthenticated-by-session route; it accepts only a per-source bearer token and writes only to that source.
- Claude Code needs to trust Remnant's certificate (`NODE_EXTRA_CA_CERTS` in managed settings) when the self-signed certificate is used.
- MCP names for user-configured servers only appear in telemetry with `OTEL_LOG_TOOL_DETAILS=1`; the guide explains that the receiver keeps the names and drops the arguments, and that the endpoint script is the other way to see them.
- The Admin API key can do more than read; the setup page says so and recommends the Analytics or Compliance key with read scopes where the plan allows.
- Built and tested against recorded, documented shapes and fake servers; live checks happen on the first install.

## Threats

| ID | Threat | ATLAS | ATT&CK | Control |
|---|---|---|---|---|
| T31 | Staff paste sensitive data into unapproved AI services | AML.T0057 LLM Data Leakage | T1567 Exfiltration Over Web Service | Shadow-AI view from network logs; AI watch alert on first sighting of a service not Approved |
| T32 | A rogue or poisoned MCP server is installed and used by an agent | AML.T0053 AI Agent Tool Invocation, AML.T0086 Exfiltration via AI Agent Tool Invocation (and the "Publish Poisoned AI Agent Tool" technique) | T1195 Supply Chain Compromise | Inventory from telemetry and endpoint configs; allowlist; alert on first sighting of a server not Approved |
| T33 | Telemetry or inventory fields carry text that instructs a model | AML.T0051.001 LLM Prompt Injection: Indirect | n/a | Same as all log content: stored as data, rendered as text, sent to a model only through the gate with the data-not-instructions prompt |
| T34 | The OTLP endpoint is flooded or fed forged records | n/a | T1499 Endpoint DoS, T1565.001 Stored Data Manipulation | Per-source token; body, record, and rate caps; records land only in the token's source and are marked with it |
| T35 | An ingest token or Anthropic key leaks | n/a | T1528 Steal Application Access Token, T1552 Unsecured Credentials | Tokens hashed and shown once, revocable; keys encrypted and write-only; read-scoped keys recommended; never logged |
| T36 | Usage data about named people is read by someone without a need | AML.T0057 (if sent to a cloud model) | T1213 Data from Information Repositories | `local_only` default; source groups; prompt and tool content dropped at the door unless an admin opts in, audited |
