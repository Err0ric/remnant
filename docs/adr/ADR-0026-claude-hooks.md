# ADR-0026: Observe Claude agent sessions with a hooks plugin that reports to this server

Status: **Accepted** 2026-10-20 (project owner: "whatever you recommend honestly. All of that sounds good"). Recorded as SPEC D68; threat T57 added.

## Context

Claude Code telemetry (ADR-0015) gives counts, cost, and tool decisions; the MCP inventory gives what is installed. Neither gives the order of events in one agent session: the prompt, each tool call with what it touched, each result, the end. That sequence is what "agents as insiders" needs (session timeline, per-agent baselines, detections). Claude Code and Claude Desktop run hooks at session start, prompt submit, before and after each tool call, and stop. Hooks can also return allow or block; this design only observes.

## Decision

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Transport | The hook script sends each event as an OTLP/HTTP JSON log record to an existing OpenTelemetry source on this server, with that source's token | Reuses the receiver, per-source tokens, content setting, and audit (ADR-0015); no new endpoint |
| 2 | Observe or enforce | Observe only. The script never returns a block, sends in the background with a 2-second timeout, and always exits 0 | A slow or down SIEM must never stop someone's work. Blocking is a guardrail product |
| 3 | Events | Session start, prompt submit, before tool use, after tool use, stop | The five that make a session timeline |
| 4 | What is sent by default | Event name, time, session id, host, OS user, client, tool name, MCP server and tool, outcome, duration, sizes. For file tools the path; for web tools the host; for shell commands the program name only. SHA-256 of prompt and tool input | Enough for timelines, baselines, and detections without content |
| 5 | Content | Off by default. The source's existing "keep content" setting (ADR-0015 row 3) turns on prompt text, tool input, and tool output, each capped at 8 KB (first and last 4 KB) | Content is the most sensitive data the server would hold; it is a deliberate choice per source |
| 6 | Where in the session | Every record carries `role`: user, tool_call, tool_result, or session | Says where in a session each record sits |
| 7 | Destination | Server URL and token are written into the plugin's config at install from the source page; nothing in a prompt, tool output, or event can change them | No redirect by injected text |
| 8 | Packaging | A Claude plugin (hooks only, no skills, no commands) built from the source page, plus a POSIX shell script and a PowerShell script that use only `curl` or `Invoke-RestMethod`. Small enough to read in one sitting; version and SHA-256 shown on the source page | Runs on every tool call, so it must be easy to review |
| 9 | Handling on the server | Records are log content: untrusted, stored with `raw` intact, never placed in instructions (security rule 2). A new template maps them to OCSF and the agents view | Same as every source |
| 10 | Coverage | Sees only Claude Code and Claude Desktop installs with the plugin. Browser chat and other vendors' agents stay visible only through network logs and the AI service catalog; the AI usage page says so | Honest boundary |
| 11 | Build order | (a) Plugin, scripts, template, session timeline in Agents. (b) Detections: new tool or destination for an agent, sensitive paths, shell after web fetch. (c) Per-agent baselines | Thin slices |

## Consequences

- Volume: one record per tool call per user. A busy developer can send thousands a day; retention for the source applies as usual.
- Removing the plugin stops the records; the session and agent views show when a machine last reported, and the device watch (ADR-0019) can alert on silence.
- ATLAS: AML.T0051 (indirect prompt injection) through tool output stored as content: stored as data, never in a prompt as instructions. AML.T0057 (data leakage): content off by default, `local_only` by default on the source. The plugin itself is code on every endpoint: AML.T0010 (ML supply chain compromise) and ATT&CK T1546 (event triggered execution) if it were tampered with, so it is pinned, hashed, and short.
- Threats: T57 (an attacker reads or alters the agent record: per-source token, HTTPS off loopback, integrity chain over the lake files, content off by default).

## Amendment 2026-10-22 (owner: build it now; pilot mode; metadata only)

Checked against Anthropic's documentation on 2026-10-22: plugin hooks load in Cowork and Claude Code (terminal, IDE, desktop Code tab) and are ignored in chat on the web, desktop, and mobile ("Plugin feature support across platforms"); Team and Enterprise Owners publish plugins org-wide from Organization settings > Plugins & skills and can make them Installed by default or Required, which also installs them in Claude Code for signed-in members ("Manage plugins for your organization").

| # | Change | Why |
|---|---|---|
| 2 | Hooks are `async: true` command hooks, so Claude Code does not wait for them at all; the script still caps the send at 2 seconds (1 to connect) and exits 0 | Never blocking does not depend on the script being fast |
| 3 | One script, `hooks/send.sh` (POSIX `sh`, `awk`, `sed`, `curl`, `sha256sum` or `shasum`). Windows runs it under Git Bash, which Claude Code uses for hooks. No PowerShell script in this version: without Git Bash, nothing is sent and the session is unaffected | Claude Code runs shell-form hooks with `sh` on macOS and Linux and Git Bash on Windows. The `http` hook type was not used: `SessionStart` accepts only command hooks, and an `http` hook posts the whole hook input, content included |
| 4 | Person: the Claude account email from `~/.claude.json` when present, else the OS user. Only `emailAddress` is read from that file | Matches the Claude Code telemetry person (`user.email`) so both feeds name the same agent |
| 5 | Content: the download sets `SEND_CONTENT` from the source's keep-content setting. When off, no prompt, tool input, or tool output leaves the machine. When on, the receiver scans the whole hook input for sensitive data once, and stores content only while the source keeps it | Metadata by default, decided per source by an admin |
| 7 | Destination: the download writes the server address and a **new** source token into the plugin's `config` (read as key=value data, never run). Earlier copies stop sending | The token is stored hashed and shown once; a dedicated source per plugin keeps this simple |
| 12 (new) | Pilot mode: `PILOT_USERS` in the config lists the people who send (email or OS user, any case). Empty: everyone who has the plugin | Rolls out to two people first without a second plugin |
| 13 (new) | Receiver path is the existing `/api/otlp/v1/logs`; records are `claude_hooks.*` events, parsed by the `claude_hooks` template; the agents view and a new sessions view (AI usage > Agents > Sessions, `/api/ai/sessions`) read them, scoped to the caller's sources | Same token, content, access, and audit rules as other OTLP senders |

ATLAS and ATT&CK, unchanged in substance: the plugin itself runs on every tool call (AML.T0010, T1546), so it is short, pinned to a version, and its script hash is shown before publishing; what it monitors is indirect prompt injection reaching agents through tool output (AML.T0051.001) and data leaving through agents (AML.T0057).


## Amendment 2026-10-29 (owner: platform plugins, managed config, account email, reference review)

Context: the owner reviewed a commercial vendor's Claude hook plugins (reference notes in the Project, `claude/notes-reference-hook-plugin.md`). Their code is not licensed and is not used; this amendment is built clean-room from the behaviors worth keeping, and keeps this ADR's observe-only design where theirs differs (theirs echoes the server's verdict to stdout, sends full content, allows env overrides of the destination, waits up to 10 s, and writes a payload debug log). Owner decisions 2026-10-29. Where a row of the 2026-10-22 amendment differs, this one wins.

| # | Change | Why |
|---|---|---|
| 3 | **One plugin per platform**, each with its own `hooks.json` and script, all exec form (`command` plus `args`, no shell): **Windows** runs `send.ps1` with `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File` (Windows PowerShell 5.1, nothing to install); **macOS and Linux** runs `send.sh` with `sh`; **Cowork** (Node) is a third plugin, built only after the pilot confirms a Cowork session can reach the server. Every script exits at once, sending nothing, on a session that belongs to another plugin: the Windows and POSIX scripts when `CLAUDE_CODE_IS_COWORK` is true or the OS is not theirs, the Cowork script unless it is true. The Git Bash dependency is gone | A single `hooks.json` for every OS asks the wrong OS to start a program it does not have; Claude Code reports a hook that cannot start. Separate plugins remove that and the Git Bash need. Gating keeps a machine with two plugins from sending twice |
| 3a | Each platform plugin is published to the people on that platform. If the admin console cannot scope a plugin to a group, the wrong-OS plugin fails to start (a non-blocking hook notice, nothing sent, the session unaffected); the pilot test list checks this | Honest about what the console allows |
| 7 | **Managed config wins.** A machine-wide file deployed by the endpoint management tool, writable by administrators only, is read first: Windows `%ProgramData%\siem-claude-hooks\hooks.conf` (SYSTEM and Administrators write, Users read), macOS `/Library/Application Support/siem-claude-hooks/hooks.conf`, Linux `/etc/siem-claude-hooks/hooks.conf` (root, 0644; the folder is named like the plugin, not the product, which is a configurable codename). When the machine file exists the plugin's own copy is not read at all, so nothing in the user's folder can change the CA or add a key. The plugin's bundled `config` is the fallback (the pilot uses it). Both are key=value data, never run. Keys: `REMNANT_URL`, `REMNANT_TOKEN`, `PILOT_USERS`, `SEND_CONTENT`, `CA_FILE`, and, read from the machine file only, `CLAUDE_EMAIL` and `DEV_ENV_OVERRIDE`. The source page downloads either the plugin with its own config (the pilot) or a bundle: the plugin with an empty config plus `hooks.conf` and a README naming where it goes | The bundled config sits in the user's plugin folder, where the user, malware, or an agent with file tools could redirect it; a machine file is not writable by them |
| 7a | Environment variables never change the destination, token, content, or CA. Only `DEV_ENV_OVERRIDE=1` **in the machine file** lets `REMNANT_URL` and `REMNANT_TOKEN` come from the environment (for testing a server build) | No redirect by anything a session can set |
| 4 | **Claude account email**, first found wins: `CLAUDE_EMAIL` from the managed config; `CLAUDE_CODE_USER_EMAIL`; `oauthAccount.emailAddress` in `$CLAUDE_CONFIG_DIR/.claude.json`, else `~/.claude.json` (that key only; no other part of the file is read or sent). Sent as `claude_account_email` with `account_from` (`managed`, `env`, or `claude_json`), always apart from `os_user`; the host name is always sent. Windows PowerShell 5.1 reads the file with `ConvertFrom-Json` and, when that fails (it refuses empty-string keys), with `JavaScriptSerializer` and a raised size limit. The email is cached in `${CLAUDE_PLUGIN_DATA}` and read again only when the file's size or time changes | The signed-in account is what ADR-0030 needs; an OS user is never mistaken for an account. The file can be several MB, too slow to parse on every tool call in PowerShell 5.1 |
| 14 (new) | Events added: **PostToolUseFailure** (`claude_hooks.post_tool_use_failure`, role `tool_result`, outcome failure) and **SessionEnd** (`claude_hooks.session_end`, role `session`). **Stop** keeps its name and becomes role `turn`, shown as "Turn end" | A failed tool call fires no PostToolUse; Stop fires every turn, not at the end of a session |
| 2 | Output: every script prints `{}` and exits 0, on every path. The receiver's response is never read into stdout, stderr, or a file. Total time capped at 2 seconds (1 to connect); every failure is silent | A compromised or impersonated receiver cannot deny a tool or add context (AML.T0051) |
| 15 (new) | **Dropped events**: a failed send appends one line to a file in `${CLAUDE_PLUGIN_DATA}`; the next successful send renames that file first and reports its line count as `dropped_since_last`. Health shows "N events dropped" per machine. Parallel hooks may lose a count; none is counted twice | A down receiver is visible without slowing anyone |
| 16 (new) | **TLS**: `CA_FILE` names an extra CA (PEM) for the server's self-signed or internal certificate (a name without a folder is a file in the plugin: the download bundles this server's generated self-signed certificate as `server-ca.pem` unless the admin unticks it): `curl --cacert` on POSIX, Node's `ca` option for Cowork, and on Windows a direct TLS 1.2 connection (`SslStream`) whose certificate check runs on the script's own thread and builds the chain with that CA as the trust anchor (a web request's check runs on another thread, where Windows PowerShell 5.1 deadlocks; found by the `hooks-windows` job). The Windows plugin connects to the server directly, not through a system proxy. There is no option to skip verification | The token travels with every record |
| 5 | **Content**: off by default; on only when the source keeps content, as before. When on, each of prompt, tool input, and tool output is capped at the source (first and last 4 KB), and the receiver masks detected secrets in what it stores, keeping the counts (ADR-0015 row 13). No debug log of payloads exists in any variant | Content is the most sensitive data the server holds (AML.T0057) |
| 17 (new) | **PowerShell execution**: `-NoProfile` always (no user profile code runs). `-ExecutionPolicy Bypass` on every tool call is the ATT&CK T1059.001 pattern defenders hunt for; an EDR may flag it, and an exclusion should be by script hash, never by command line. Signed option: the admin Authenticode-signs `send.ps1` with the organization's code-signing certificate (off the server; the key never touches it), uploads the signed script on the source page, and the Windows plugin then runs with `-ExecutionPolicy AllSigned`. The source page shows each script's SHA-256 and whether it is signed. A Group Policy execution policy overrides the command-line flag either way | No Bypass where the organization can sign |
| 18 (new) | **Deployment**: a pilot guide (publish per platform to the org with `PILOT_USERS`, the forward-auth exemption for `/api/otlp/v1/logs` only, and a test list: one record of each event; a stopped receiver adds no delay; a receiver answering 403 or a crafted body changes nothing in Claude; a receiver that hangs 30 s adds no delay; the wrong-OS plugin sends nothing). Pass/fail (owner, 2026-10-29): if a wrong-OS plugin shows a hook notice on every tool call, not once per session, the per-platform approach fails as published, and the fallback is scoping each plugin to a group in the admin console, or a single launcher that picks the script per OS | The owner's pilot checks |

Build order (owner, 2026-10-29): (a) this amendment and the ADR-0030 tiers; (b) the Windows and POSIX plugins, managed config, account email, events, TLS, dropped count with its Health line, and the pilot guide; (c) the Cowork plugin after the reachability check; (d) ADR-0030 evidence, after ADR-0029 parts 2 and 3.
