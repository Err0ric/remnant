# Microsoft 365: audit logs, Entra sign-ins, and security alerts

The Microsoft 365 source reads your tenant's audit records, Entra ID sign-ins and directory changes, and (optionally) Microsoft security alerts, every 5 minutes, with a read-only app registration. Each record is stored as Microsoft's JSON, unchanged, in `raw`, and parsed into the usual columns. Design: [ADR-0002](../adr/ADR-0002-m365-connector.md).

What you get:

| Feed | What is in it | Parsed as |
|---|---|---|
| Entra ID audit (`Audit.AzureActiveDirectory`) | Sign-in successes and failures as seen by the audit log, user and app changes | API Activity |
| Exchange (`Audit.Exchange`) | Mailbox access, inbox rules, send-as, admin cmdlets | API Activity |
| SharePoint and OneDrive (`Audit.SharePoint`) | File views, downloads, sharing links, site changes | API Activity |
| General (`Audit.General`) | Teams, Forms, Power Platform, and **Copilot interactions** (which app, which files it used) | API Activity |
| DLP rule matches (`DLP.All`) | Which policy and rule matched, where, for whom | API Activity, severity Medium |
| Sign-ins (Graph) | Every interactive and non-interactive sign-in: app, IP, device, location, conditional access, risk | Authentication |
| Directory changes (Graph) | Role, group, app, and policy changes, with who made them | Entity Management |
| Security alerts (Graph) | Defender, Entra ID Protection, Purview DLP, and other Microsoft alerts | Detection Finding |

Nothing is ever written to your tenant. The app has read permissions only.

## Before you start

| Need | Notes |
|---|---|
| An Entra role that can register apps and grant admin consent | Global Administrator, or Application Administrator plus Privileged Role Administrator for consent |
| Unified audit logging on | On by default in most tenants. Check in the Microsoft Purview portal under **Audit**; if it offers **Start recording user and admin activity**, turn it on and wait up to 60 minutes |
| Entra ID P1 or P2 | Only for the **Sign-ins** feed. Without it that feed shows a warning and the others still work |
| Outbound HTTPS from the server | To `login.microsoftonline.com`, `manage.office.com`, and `graph.microsoft.com` (GCC: `manage-gcc.office.com`; GCC High: `login.microsoftonline.us`, `manage.office365.us`, `graph.microsoft.us`), directly or through a proxy ([proxy.md](proxy.md)) |

## 1. Register the app

In the [Microsoft Entra admin center](https://entra.microsoft.com), open **App registrations**, then **New registration**.

| Field | Value |
|---|---|
| Name | Anything recognizable, for example `SIEM log reader` |
| Supported account types | **Accounts in this organizational directory only** (single tenant) |
| Redirect URI | Leave empty |

After **Register**, copy from the **Overview** page:

- **Directory (tenant) ID**
- **Application (client) ID**

If you also use Entra sign-in for the web UI ([sso-entra.md](sso-entra.md)), make this a **separate** app. The sign-in app should never hold audit permissions.

## 2. Add the permissions

Open **API permissions**, then **Add a permission**. Add **Application permissions** (not Delegated) only for the feeds you will turn on:

| API | Permission | For |
|---|---|---|
| **Office 365 Management APIs** | `ActivityFeed.Read` | Entra ID audit, Exchange, SharePoint, General (Copilot) |
| **Office 365 Management APIs** | `ActivityFeed.ReadDlp` | DLP rule matches |
| **Microsoft Graph** | `AuditLog.Read.All` | Sign-ins and directory changes |
| **Microsoft Graph** | `SecurityAlert.Read.All` | Security alerts |

Then select **Grant admin consent for (your tenant)** and confirm. Every row should show a green **Granted** status. Without consent, the test in step 5 says which API refused access.

The consent screen your admin sees lists exactly these permissions, each marked **Application** and **Read**. Nothing else is requested.

## 3. Create a credential

A certificate is the safer choice: the private key never leaves the server, and nothing reusable crosses the network. A client secret is simpler but is a password that expires within two years.

### Certificate (recommended)

On any machine with OpenSSL (the server itself is fine):

```bash
openssl req -x509 -newkey rsa:3072 -nodes -days 730 \
  -subj "/CN=siem-log-reader" \
  -keyout m365-reader.key -out m365-reader.crt
```

In the app registration, open **Certificates and secrets**, then **Certificates**, then **Upload certificate**, and upload `m365-reader.crt`. Note the **Thumbprint** Entra shows.

Keep `m365-reader.key` only long enough to paste it into the form, then delete it. The server stores it encrypted with its install key.

### Client secret

**Certificates and secrets**, then **Client secrets**, then **New client secret**. Copy the **Value** (not the Secret ID) right away; Entra shows it once.

## 4. Add the source

**Sources > Add source**, then **Reads from: Microsoft 365**.

| Field | Value |
|---|---|
| Source ID | For example `m365` |
| Parser | Leave **Automatic**: each record goes to the matching Microsoft template |
| Directory (tenant) ID, Application (client) ID | From step 1 |
| Cloud | Commercial, GCC, or GCC High |
| Sign in with | Certificate or Client secret, matching step 3 |
| Certificate and private key | Paste the full PEM text of each, including the `BEGIN` and `END` lines |
| Audit logs, Microsoft Graph | Tick the feeds you granted permissions for in step 2 |
| On first run, read back | Hours of history to read the first time. Default and maximum 168 (the audit API keeps 7 days). A busy tenant's 7 days can be hundreds of thousands of events; the first runs catch up over several polls |

## 5. Test, then save

Select **Test connection**. It signs in and makes one small read per API: for the audit logs it lists the tenant's subscriptions (read only; Test never starts one, D92), for Graph it reads a page of each ticked feed:

- **Works** next to each feed: save the source. On a new app the audit line reads **Works. No subscription yet for ...; it starts when the source is added.** That is normal: the source starts the subscriptions on its first run.
- **Certificate thumbprint**: it should match the one Entra showed in step 3. If not, the wrong certificate was uploaded.
- A reason next to a feed: the common ones are below.

| Message | Fix |
|---|---|
| the certificate is not uploaded to the app registration, or does not match (AADSTS700027) | Upload the `.crt` from step 3 to this app |
| the client secret is wrong or expired (AADSTS7000215, 7000222) | Make a new secret and use **Replace credentials** |
| no app with this client id in the tenant (AADSTS700016) | Check the client and tenant ids are from the same app |
| refused access (HTTP 401 or 403); check the app's API permissions and admin consent | Step 2: the permission is missing or consent was not granted |
| Sign-in logs need Entra ID P1 or P2 in this tenant | Untick **Sign-ins**, or license the tenant |
| ... (AF10001) the app lacks ActivityFeed.Read | Step 2: add **Office 365 Management APIs > ActivityFeed.Read** and grant admin consent |
| ... (AF20012) the tenant is not set up for the audit API | Turn on audit logging (Purview > Audit), then wait up to a day |
| ... (AF20023) the subscription was turned off | Someone stopped it in the tenant; the source starts it again on its next run |
| Any other `(AFnnnnn)` code | Microsoft's own message is shown next to the code; see Microsoft's Management Activity API troubleshooting reference |
| answered HTTP nnn: (text) | An unexpected reply; the first 200 characters of the body are shown so it can be looked up |

The first records can take a while: Microsoft makes audit content available 30 minutes to several hours after the activity, and sign-ins a few minutes after. The Sources page shows how far behind the source is.

## Day to day

- **Journal:** the service log has a line per connector event, with the source id: `connector_notice` (a subscription started), `connector_pulled` (events read and how far behind, when there were events or after a recovery), `connector_feed_failed` (one feed failed, logged when it starts failing), and `connector_failed` (every feed failed, with the next retry). For example `journalctl -u <service> | grep connector_`.
- **Changing it later:** on **Sources**, **Edit settings** changes the feeds and the history read for newly added feeds; **Change** next to Retention changes how many days are kept (the nightly job applies it). Both keep the stored certificate or secret and are audited (`source.settings_change`, `source.retention_change`). The tenant, app, cloud, and sign-in method go with the credential: use **Replace credentials** or add a new source.
- **Two kinds of Entra sign-in rows:** the audit logs' Entra feed (`m365_management_activity`, `UserLoggedIn` and `UserLoginFailed`) repeats the Graph sign-ins (`m365_signin`) in a thinner form. Keep both if you like; the Graph rows are the richer ones (application, conditional access, risk, device, location). In `m365_signin`, `message` is the application signed in to (`appDisplayName`); the resource is in `raw` (`resourceDisplayName`).

- **Status:** a feed that fails while others work shows as a warning under the source. If every feed fails, the source shows the error and retries with growing waits (or as Microsoft asks, when it throttles).
- **Renewing the certificate or secret:** upload the new certificate to the app (keep the old one until the switch), then **Sources > (the source) > Replace credentials**. Reading continues from where it was.
- **Classification:** like every source, it starts `local_only`, so none of it goes to a cloud AI provider unless an administrator changes that.
- **Who sees what:** only administrators see the tenant id, feeds, and warnings. Grant the source to a group on **Users and access** for analysts to search it.
- **Searches to start with:** `message = 'CopilotInteraction'` (who used Copilot, in which app), `message = 'DlpRuleMatch'` (DLP hits), `class_uid = 3002 AND status_id = 2` (failed Graph sign-ins), `message = 'UserLoginFailed'` (failed logons in the audit logs; their status is 2 from template version 1.1.0, F42), `template_id = 'm365_directory_audit' AND severity_id >= 3` (role, credential, and conditional access changes).

## Removing it

Delete the source on the Sources page (events already stored stay until retention removes them), then delete the app registration in Entra. Deleting the app revokes the certificate or secret at once.
