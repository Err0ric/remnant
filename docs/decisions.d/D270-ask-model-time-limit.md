| D270 | A time limit on each Ask model call, and a smaller summary input (owner, 2026-11-17, pre-approved for this batch). Setting `ask.model_timeout_s` (default 90, 5 to 3600): the gate gives every Ask call (routing, query writing, summary) a deadline; the adapters' HTTP client holds one deadline from the start of the request across connect, the headers, and every read (the time left, read as each step starts, and the socket shut at the deadline; the read has no fixed limit of its own under it, so a setting above 180 is honoured, and a read timeout under a deadline is always the time-limit outcome), so no provider request keeps running untracked. Waiting for the model's queue is not counted (ADR-0028 keeps its own budget). The call is audited with error `timeout` (`llm_calls`) and the Ask audit row with `ModelTimeoutError`. A timed-out query call ends the job with "The model took too long to write a query." (HTTP 504 `model_timeout` on the synchronous call); a timed-out summary keeps the rows and SQL and says "The model took too long to summarize. Results are above." Explain, parser drafts, and reports keep the existing per-read limit. The summary call (`ask_answer.v2`) gets at most 10 rows plus per-column stats over every kept row, computed by code: counts and distinct counts, min and max for numbers and times, true and false counts for booleans, and no text value ever (the stats cover rows not sent, and a renamed column such as `actor_user_name AS who` would carry names past the redactor), within the 7,000 characters the 20 rows had; only the rows sent may be cited.
